# Translatable strings

Full rule: `.cursor/rules/wp-i18n.mdc`.

Current state — factual, **do not "fix" unasked**: ~3,800 `__()` calls in `src/` and ~110 in
`includes/` already use the `twork-builder` domain, but `languages/` ships no `.pot`, and neither
`load_plugin_textdomain()` nor `wp_set_script_translations()` is called. Strings are marked up
correctly; nothing is actually translated at runtime. Wiring that up is a separate approved task.

Hard guards:

- Every user-facing string through `__()` / `_x()` / `_n()` / `esc_html__()` with the literal
  `'twork-builder'` domain — never a variable or constant for the domain
- Never concatenate a sentence; use `sprintf()` with numbered placeholders (`%1$s`, `%2$s`)
- `_n()` for plurals; `/* translators: … */` comments for anything ambiguous
- Never wrap a CSS class, HTML attribute value, `rel="noopener"`, block name, or option key in `__()`
- Editor-changeable copy belongs in a `block.json` attribute default, **not** in a translation call —
  `__()` is for editor UI chrome and unreachable front-end chrome
- Dates via `wp_date()` / `date_i18n()`; numbers via `number_format_i18n()`
- No RTL retrofit — this plugin ships no RTL build
